{% docs ama_answer %}
An **AMA answer** is one response generated by "Ask Me Anything", Lexroom's legal Q&A module. One row in `raw_events_ama` is one answer. Exact duplicate rows in the raw export are removed.
{% enddocs %}

{% docs event_week %}
The week the answer was generated, as the Monday that starts it (ISO week, UTC). All weekly metrics use this date.
{% enddocs %}

{% docs is_timeout %}
True when the answer hit the backend hard timeout (latency recorded as exactly 900,000 ms, i.e. 15 minutes). Only 6 of the 28 timeouts were rated, but 5 of those 6 were thumbs down: we count them as a failure, not as noise.
{% enddocs %}

{% docs has_no_sources %}
True when the RAG step retrieved zero sources. This is a product definition, not a finding: for a legal assistant an answer without sources should not be trusted, so it counts as a failure even though users rated 13 of 20 such answers positively.
{% enddocs %}

{% docs technical_success_rate %}
Share of answers that were delivered without a timeout and with at least one retrieved source. It covers 100% of answers, because it does not depend on users leaving feedback.
{% enddocs %}

{% docs thumbs_down_rate %}
Thumbs down divided by rated answers (thumbs up + thumbs down). Only about 27% of answers are rated, so this rate is noisy on small volumes: check `is_low_sample` before reading it.
{% enddocs %}

{% docs good_answer_rate %}
**AMA North Star.** The estimated share of answers that were both technically sound and found useful:

`good_answer_rate = technical_success_rate × (1 − thumbs_down_rate_successful)`

i.e. P(technically sound) × P(not rated down | technically sound).

- **Grain:** one value per week (or per module per week).
- **Window:** weekly, read as a trend over the last 8 weeks up to `as_of_date`.
- **Assumption:** users who rate are representative of those who don't. On everything we can observe (latency, tokens, sources, cache, module, role) rated and unrated answers look the same; selection on satisfaction itself cannot be ruled out.
{% enddocs %}

{% docs is_low_sample %}
True when fewer than 30 answers were rated in the period (`min_rated_answers` variable). Rates computed on such periods should not drive decisions.
{% enddocs %}

{% docs risk_score %}
**Account health risk** for Customer Success, from 0 to 100, comparing the 28 days up to `as_of_date` with the 28 days before. Every signal is also computed one week earlier.

| Signal | Points | Fires when |
|---|---|---|
| Quality drop | 40 if also present one week earlier, 20 if only this week | Thumbs-down rate at least 10 points higher than in the previous period (min 15 rated answers in both) |
| Usage drop | 30 | Answers below half of what the platform trend predicts for this workspace (min 30 answers before) |
| Users drop | 20 | Active users below half of what the platform trend predicts (min 5 users before) |
| Failed answers | 10 | At least 3% of answers timed out or had no sources (min 20 answers) |

`risk_level`: **high** ≥ 40, **medium** 20 to 39, **low** below 20 with enough ratings to judge, **not enough data** below 20 without them (low does not mean healthy unless we could measure it).

Usage signals are relative to the platform: when everyone uses AMA less, that is a product question, not an account one.
{% enddocs %}

{% docs is_after_as_of_date %}
True for data after the `as_of_date` var. By default `as_of_date` is the last day in the data (19 April 2026), so this is false everywhere; moving the var back shows how sensitive the answers are to the window.
{% enddocs %}
